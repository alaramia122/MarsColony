# Инструкции для ИИ-агентов

Этот файл задаёт обязательный порядок работы с репозиторием MarsColony. Репозиторий является основным переносимым источником контекста проекта. Не полагайтесь на историю чатов и не считайте устные обсуждения актуальными требованиями, пока они не зафиксированы здесь.

## Обязательное чтение перед работой

1. `README.md` — назначение и навигация.
2. `docs/PROJECT_STATE.md` — текущее состояние, открытые вопросы и следующий шаг.
3. `docs/GDD.md` — игровой опыт и правила.
4. `docs/TECHNICAL_SPEC.md` — технические требования и критерии приёмки.
5. `docs/ECONOMY_MODEL.md` — предметная и расчётная модель экономики.
6. Все относящиеся к задаче документы в `docs/decisions/` — принятые архитектурные решения.

Если задача затрагивает только один ограниченный документ, всё равно прочитайте PROJECT_STATE и соответствующий профильный документ.

## Приоритет источников

- Принятые требования в GDD и TECHNICAL_SPEC определяют ожидаемое поведение продукта.
- ECONOMY_MODEL определяет экономические понятия, балансы и правила расчётов.
- ADR фиксируют причины и последствия архитектурных решений.
- PROJECT_STATE отражает актуальное положение дел, но не отменяет требований и ADR.
- Issues уточняют объём конкретной работы; PR показывает предлагаемые изменения.
- История чата является контекстом обсуждения, но не заменяет зафиксированные решения.

При противоречии не выбирайте вариант молча. Зафиксируйте конфликт, укажите затронутые документы и предложите согласованное решение.

## Правила работы

- До изменения файлов проверьте текущую ветку, последние изменения и актуальное содержимое затрагиваемых файлов.
- Не перезаписывайте изменения пользователя и не используйте устаревшие версии документов.
- Не объединяйте Pull Requests и не меняйте `main` без явного разрешения владельца проекта.
- Работайте небольшими логическими изменениями через ветки и Pull Requests.
- Не выдумывайте источники, численные параметры, результаты тестов или статус реализации.
- Разделяйте подтверждённые физические/инженерные данные, проектные решения и игровые допущения.
- Для численных параметров указывайте единицы измерения, временную базу, источник или обоснование и статус достоверности.
- Серверная доменная логика остаётся источником истины; LLM не изменяет игровое состояние напрямую.
- Сохраняйте провайдер-независимую интеграцию ИИ и не предполагайте, что подписка ChatGPT Plus предоставляет API-кредиты.
- Документы формулируйте через требуемое поведение, проверяемые критерии и явно обозначенные допущения.
- Не усложняйте MVP функциями, которые не нужны для проверки основного игрового цикла.

## Обязательное завершение задачи

1. Запустить доступные проверки и указать фактический результат.
2. Обновить документацию, если изменились поведение, интерфейсы, данные, архитектура или ограничения.
3. Обновить `docs/PROJECT_STATE.md`, если изменились этап, статус, открытые вопросы или следующий шаг.
4. В PR описать цель, изменения, проверки, известные ограничения и оставшиеся вопросы.
5. В итоговом отчёте перечислить изменённые файлы, ссылки и непроверенные предположения.


## Сценарные данные и контрольные расчёты

- Машиночитаемые параметры сценариев хранятся в `data/scenarios/`; человекочитаемое описание, источники и допущения — в соответствующем документе `docs/SCENARIO_*.md`.
- При изменении параметров синхронно обновляйте описание, контрольный расчёт и тесты.
- Эталонные скрипты из `tools/` служат проверке проектных решений и не должны становиться скрытой runtime-зависимостью игрового backend.
- После изменения сценария запускайте:
  ```bash
  python -m json.tool data/scenarios/ares-01.json
  python -m unittest discover -s tests -v
  python tools/scenario_sim.py
  ```
- В численных отчётах показывайте единицы измерения, временную базу, исходные значения и округление. Не смешивайте земные сутки и марсианские солы.
- Не называйте сценарий сбалансированным или подтверждённым до плейтеста. Автоматические тесты подтверждают арифметическую согласованность заданной модели, а не физическую реализуемость базы.
