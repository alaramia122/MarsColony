## Назначение

MarsColony — многопользовательская настольная стратегическая НРИ о развитии марсианской колонии с цифровым сопровождением. MVP — локальная сессия до трёх часов, браузерные клиенты в домашней сети, общий экран и голосовой интерфейс через Яндекс Алису.

## Принятые решения

- Backend: Python 3.12+, FastAPI, Pydantic.
- Frontend: React, TypeScript, Vite.
- PostgreSQL — постоянное хранилище; WebSocket — обновление клиентов.
- Docker Compose и GitHub Actions; на старте модульный монолит.
- Сервер — единственный источник игрового состояния; LLM формирует типизированные предложения, сервер проверяет и применяет подтверждённые команды.
- Алиса и веб-клиенты используют единый API; AI Gateway не привязан к одному провайдеру.
- Экономика включает материальную, энергетическую, биологическую, демографическую, финансовую и технологическую подсистемы.
- Базовый численный сценарий — Ares-1: 24 человека, четыре периода по 30 солов.
- При калибровке используются российские и международные инженерные источники. Численные параметры получают источник, условия измерения, временную базу и оценку применимости.

## Этап 1 — игровое ядро и экономика

### Уже интегрировано в main

- Детерминированный расчёт четырёх периодов Ares-1.
- Балансы кислорода, сухих пищевых веществ, воды, сырого льда и бюджета.
- Сводка генерации и потребления электроэнергии и проверка резерва при обслуживании энергомодуля.
- FastAPI для создания сессии, чтения состояния и продвижения периода.
- PostgreSQL-модели сессий и append-only журнала событий.
- Alembic initial migration, Docker Compose и CI с PostgreSQL 16.

### Текущий рабочий срез

В PR #6 (`feat/stage1-economic-engine`) реализованы:

- универсальный исполнитель материальных процессов с ограничением по входным запасам, энергии и вместимости складов;
- расчёт процессов Ares-1 для кислорода, тепличной продукции и воды через общий исполнитель;
- детерминированное распределение электрической мощности между критическими и гибкими нагрузками при обслуживании энергомодуля;
- учёт длительности обслуживания в генерации, потреблении, ограничении нагрузки и расходе энергетического резерва;
- явная регистрация финансового дефицита без отрицательного остатка бюджета;
- фиксация снимка сценария при создании сессии;
- защита команды продвижения периода от устаревшего состояния через `expected_period`;
- интеграционные проверки полного сценария непосредственно на PostgreSQL в CI;
- актуализация документации и CI-проверка Compose.

## Критерий готовности этапа 1

Сервер создаёт сессию из неизменяемого снимка сценария, рассчитывает все четыре периода Ares-1 детерминированно, сохраняет состояние и журнал в PostgreSQL, отклоняет некорректные и устаревшие команды, проходит тесты на реальном PostgreSQL 16 и запускается через Docker Compose.

Плейтест не проводится до готовности локальной многоклиентской платформы; Issue #3 остаётся открытой.
