# Этап 4 — AI Gateway и ИИ-ведущий

**Статус:** полный функциональный срез реализован; CI успешно пройден. Реальная проверка Yandex API ожидает пользовательские credentials.  
**Ветка:** feat/stage4-ai-gateway-game-master

## 1. Цель

Добавить к игровому ядру ИИ-ведущего, который анализирует фактическое состояние колонии, формирует оперативные сводки, помогает игрокам описывать проекты естественным языком, предлагает сценарные события и поддерживает версионируемый реестр знаний.

ИИ выполняет роль аналитического и сценарного помощника. Игровое состояние остаётся под контролем backend и участников сессии.

## 2. Архитектура

- AI Gateway отделяет игровые модули от протокола и поставщика модели.
- Реализованы адаптеры OpenAI Chat Completions-compatible API и нативного Yandex AI Studio Foundation Models API. OpenAI-compatible интерфейс позволяет подключать провайдеров с совместимым протоколом, включая локальные шлюзы.
- Поддерживается реестр нескольких конфигураций MARS_AI_PROVIDERS и маршрутизация задач MARS_AI_TASK_ROUTING; для каждой задачи задаётся упорядоченный список резервных провайдеров.
- Профиль провайдера задаёт тип адаптера, base URL, модель, имя переменной окружения с API-ключом, лимит токенов и поддержку JSON mode. Секреты не записываются в JSON-конфигурацию.
- Реализован последовательный fallback при ошибке провайдера. Все результаты проходят единые Pydantic- и доменные проверки.
- Провайдер выбирается через окружение. По умолчанию AI выключен.
- Модели получают минимальный структурированный контекст: состояние ресурсов, инфраструктуру, технологии, участников, проекты и последние события. Сессионные токены, хеши, секреты и доступ к БД модели не передаются.
- Ответ модели считается недоверенным и проходит Pydantic-валидацию, затем доменную проверку backend.
- Модель не получает инструментов, SQL, команд продвижения периода или прямого доступа к игровому состоянию.

## 3. Функциональные контуры

### 3.1. Естественный язык → проект

Игрок описывает инициативу. AI Gateway формирует типизированное предложение с:
- названием, описанием, типом и направлениями;
- бюджетом, сроком, трудом FTE и энергией;
- требованиями к ресурсам и ожидаемыми результатами;
- обоснованием, допущениями, рисками и вопросами.

Backend проверяет полномочия автора, коды направлений, тип проекта, численные пределы, доступный каталог ресурсов и допустимые эффекты. Предложение хранится отдельно со статусом pending_review.

Игрок может уточнять предложение в диалоге; каждый ответ создаёт новую версию, а предыдущие версии сохраняются. Также игрок может отклонить предложение или явно преобразовать его в обычный проектный черновик. После создания черновика используются существующие механизмы отправки, независимых согласований, резервирования ресурсов, исполнения и аудита.

### 3.2. Оперативная сводка колонии

ИИ формирует сводку из актуального snapshot сессии и последних событий: краткая ситуация, ключевые изменения, риски, вопросы, требующие решения, и фокус следующего периода. Сводка маркируется номером периода, для которого был собран контекст. Модель должна отделять наблюдаемые факты от оценок и не добавлять неизвестные значения.

### 3.3. Сценарные события

Командир может запросить предложение события. Контракт содержит категорию, уровень серьёзности, оценочную вероятность, условие/триггер, описание, варианты действий, возможные последствия и допущения.

Предложение сохраняется отдельно и ожидает решения командира. При публикации оно записывается в общий журнал событий и передаётся всем клиентам через WebSocket. Отклонение также фиксируется в журнале.

Публикация события добавляет сценарную карточку в игровой журнал. Ресурсы, инфраструктура и другие показатели автоматически не меняются: последствия разрешаются участниками через обычные игровые механики и команды.

### 3.4. Реестр знаний и версий

Игроки с полномочиями командира, руководителя направления или инженера могут предложить сущность одного из типов: технология, инфраструктура, процесс, ресурс или процедура.

Каждая запись содержит стабильный ключ, описание, направления, структурированное определение, исходный текст, допущения и риски. Новая запись получает следующую версию ключа и статус pending_review.

Командир может утвердить или отклонить запись. Утверждение переводит новую версию в active, а предыдущую активную версию того же ключа — в superseded. История версий остаётся доступна.

Реестр является базой знаний сессии. Утверждение сущности само по себе не меняет экономическую модель, каталоги ресурсов, производство или расчёты. Для этого потребуется отдельное инженерное изменение и тестирование.

## 4. API

### Проектные предложения
- POST /api/v1/sessions/{session_id}/ai/proposals
- GET /api/v1/sessions/{session_id}/ai/proposals
- POST /api/v1/sessions/{session_id}/ai/proposals/{proposal_id}/clarify
- POST /api/v1/sessions/{session_id}/ai/proposals/{proposal_id}/create-project
- POST /api/v1/sessions/{session_id}/ai/proposals/{proposal_id}/reject

### ИИ-ведущий
- POST /api/v1/sessions/{session_id}/ai/briefing
- POST /api/v1/sessions/{session_id}/ai/events
- GET /api/v1/sessions/{session_id}/ai/events
- POST /api/v1/sessions/{session_id}/ai/events/{proposal_id}/publish
- POST /api/v1/sessions/{session_id}/ai/events/{proposal_id}/reject

### Реестр знаний
- POST /api/v1/sessions/{session_id}/ai/entities
- GET /api/v1/sessions/{session_id}/ai/entities
- POST /api/v1/sessions/{session_id}/ai/entities/{entity_id}/approve
- POST /api/v1/sessions/{session_id}/ai/entities/{entity_id}/reject

Все endpoints требуют X-Player-Token. Проверка полномочий выполняется на сервере при каждом действии. Значимые переходы попадают в append-only журнал событий.

## 5. Конфигурация

### Отключённый режим
MARS_AI_PROVIDER=disabled — значение по умолчанию. AI endpoints возвращают контролируемую ошибку 503; обычная игровая система продолжает работать.

### Yandex AI Studio
- MARS_AI_PROVIDER=yandex_ai_studio
- MARS_AI_YANDEX_API_KEY
- MARS_AI_YANDEX_FOLDER_ID
- MARS_AI_YANDEX_MODEL=yandexgpt/latest (можно передать полный model URI)
- MARS_AI_TIMEOUT_SECONDS=45

Используется нативный endpoint https://ai.api.cloud.yandex.net/foundationModels/v1/completion, заголовок Authorization: Api-Key, x-folder-id, поле modelUri и JSON-режим jsonObject. Для API-ключа требуется scope yc.ai.foundationModels.execute; сервисному аккаунту требуется роль ai.languageModels.user в каталоге. API оплачивается по потреблению; бесплатность не предполагается.

### Несколько провайдеров и маршрутизация
`MARS_AI_PROVIDERS` — JSON-объект именованных профилей. Поддерживаемые типы: `openai_compatible` и `yandex_ai_studio`. Для OpenAI-compatible профиля задаются `base_url`, `model`, `api_key_env`, `requires_api_key`, `max_tokens` и `capabilities.json_object`. Для Yandex задаются `api_key_env`, `folder_id` и `model`.

`MARS_AI_TASK_ROUTING` — JSON-объект, сопоставляющий задачу с именем профиля или упорядоченным списком профилей. Имена задач: `project_proposal`, `project_clarification`, `briefing`, `scenario_event`, `knowledge_entity`. При сбое выполняется переход к следующему профилю. Конфигурация профилей имеет приоритет над legacy single-provider переменными.

Пример локальной модели:

```json
{"local":{"type":"openai_compatible","base_url":"http://ollama:11434/v1","model":"qwen2.5:7b","requires_api_key":false,"capabilities":{"json_object":false}}}
```

### OpenAI-compatible (legacy single-provider)
- MARS_AI_PROVIDER=openai_compatible
- MARS_AI_BASE_URL
- MARS_AI_API_KEY
- MARS_AI_MODEL
- MARS_AI_TIMEOUT_SECONDS=45

Пример локальной конфигурации находится в .env.example. Секреты не коммитятся.

## 7. Безопасность и отказоустойчивость

- Текст игрока рассматривается как недоверенные данные; инструкции в нём не могут менять роль модели или игровые ограничения.
- Модель не может выполнять инструменты или команды.
- Входные тексты ограничены по размеру; HTTP-запрос имеет ограниченный timeout; размер ответа ограничен 1 МБ.
- Для контроля расходуемых API-квот действует лимит 8 AI-запросов на участника в час и 40 запросов на игровую сессию в час; счётчик хранится в PostgreSQL.
- Yandex-адаптер принимает только финальную альтернативу; частичный, усечённый или отфильтрованный ответ не используется.
- Ответы проверяются схемами и доменными ограничениями.
- Действия создания черновика, публикации события и утверждения сущности доступны только в пределах серверных полномочий.
- Контекст генерируется повторно при каждом запросе; при изменении журнала событий или периода во время генерации запись отклоняется как устаревшая.
- Конфликты версий и повторные переходы блокируются.
- AI не изменяет состояние экономики напрямую.

## 8. Проверки и критерии приёмки

CI должен подтверждать:
1. Контрактные тесты Pydantic и конфигурацию обоих провайдеров.
2. Native Yandex request shape и обработку завершённого JSON-ответа через mock HTTP.
3. Создание, просмотр, уточнение и версионирование проектных предложений.
4. Явное создание черновика и запрет повторного преобразования.
5. Генерацию сводки из контекста сессии.
6. Создание, публикацию и отклонение сценарного события; проверку полномочий командира.
7. Создание, утверждение, отклонение и supersede предыдущей версии сущности.
8. Миграции PostgreSQL, API и frontend typecheck/build.
9. Сборку и запуск Compose, smoke и recovery.

Реальный вызов Yandex AI Studio требует пользовательских ключа и folder ID; секреты не запрашиваются и не хранятся в репозитории. До настройки этих значений тестируется протокол на mock HTTP.
