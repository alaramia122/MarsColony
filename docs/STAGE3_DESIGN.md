# Этап 3 — веб-клиенты, карта и синхронизация

**Связанная задача:** [Issue #9](https://github.com/alaramia122/MarsColony/issues/9)  
**Рабочая ветка:** `feat/stage3-web-clients-map`

## 1. Назначение

Этап 3 предоставляет браузерный интерфейс локальной игровой сессии: общий экран колонии и персональные кабинеты. Оба режима получают данные из одного backend API и отображают единое серверное состояние.

## 2. Архитектура

- React + TypeScript + Vite — единое адаптивное веб-приложение.
- FastAPI остаётся владельцем игрового состояния и единственной точкой применения команд.
- HTTP используется для запросов состояния и игровых команд.
- WebSocket используется для доставки уведомлений о новых записях append-only журнала.
- PostgreSQL остаётся постоянным источником истории; WebSocket-соединение не является хранилищем.
- Nginx отдаёт собранный frontend и проксирует `/api/` к backend, включая Upgrade для WebSocket.
- Docker Compose публикует web-клиент на порту 8080 и API на порту 8000.

## 3. WebSocket протокол

Endpoint: `/api/v1/sessions/{session_id}/stream`.

После установки соединения клиент первым сообщением передаёт:

```json
{"type":"authenticate","player_token":"<session-scoped-token>"}
```

Токен передаётся внутри первого сообщения, а не query-параметром URL. Сервер проверяет SHA-256 хеш токена в контексте указанной сессии. При ошибке соединение закрывается с кодом 4401; неизвестная сессия — 4404.

После аутентификации сервер отправляет полный `snapshot` и номер последнего события. Затем сервер периодически читает PostgreSQL и передаёт записи с большей последовательностью:

```json
{"type":"event","sequence":12,"event_type":"period.completed","payload":{},"created_at":"..."}
```

Heartbeat передаётся каждые 15 секунд. Клиент после получения события обновляет HTTP snapshot. При первичной загрузке и восстановлении также отображаются последние 12 записей истории с серверными временными метками. Таким образом, событие является сигналом обновления, а не самостоятельной командой изменения клиентского состояния.

## 4. Согласованность и восстановление

Сервер читает только уже зафиксированные строки журнала. Периодические транзакции и проектные операции сохраняют изменение состояния и audit event вместе. WebSocket-поллинг видит событие после commit.

При разрыве соединения клиент переподключается и получает новый полный snapshot. Это обеспечивает восстановление актуального состояния независимо от того, сколько уведомлений было пропущено. Повторное уведомление безопасно: клиент перечитывает состояние с сервера, а не повторно применяет event payload.

Текущая реализация использует polling PostgreSQL с интервалом 750 мс. Это простой переносимый механизм для LAN MVP. При росте количества одновременных сессий можно заменить его на PostgreSQL LISTEN/NOTIFY или внутренний брокер, сохранив формат протокола и журнал как источник истины.

## 5. Клиентские режимы

- **Обзор:** период, кислород, подготовленная вода, пищевые запасы, бюджет, энергетика, инфраструктура, технологии, проекты и последние события.
- **Общий экран:** тот же обзор в полноэкранной компоновке через `?view=screen`.
- **Персональная работа с проектами:** создание черновика, отправка на согласование, согласование/отклонение, запуск, подтверждение завершения и отмена. Форма включает несколько направлений, бюджет, длительность, FTE, энергию за период, требования к четырём сценарным ресурсам и ожидаемый выпуск/эффекты инфраструктуры и энергетики. Карточка показывает материальные входы и ожидаемые эффекты. Backend проверяет полномочия, бюджет, ресурсы и версию проекта при каждой команде.
- **Продвижение периода:** командир запускает следующий период из обзора; команда передаёт `expected_period`, чтобы сервер отклонил устаревшее действие.
- **Карта:** схематическое отображение базового модуля и инфраструктурных объектов. Переключатели слоёв формируются из реально присутствующих типов объектов. Маркеры размещаются только при наличии координат `properties.x` и `properties.y` в диапазоне 0–100.
- **Участники:** состав сессии, роли, направления и технологические записи. Командир назначает и меняет роли и зоны ответственности; интерфейс учитывает необходимость назначить домены руководителям направлений и инженерам. Backend сохраняет защиту от удаления последнего командира.

Если координаты объекта отсутствуют, он показывается в отдельном списке неразмещённых объектов. UI не выводит фиктивную геометрию как данные сценария.

Форма проекта задаёт ресурсные требования, труд, энергию и типизированные результаты, поддерживаемые backend. Редактор ролей и направлений использует существующий API управления полномочиями.

## 6. Аутентификация и границы доверия

Сессионный токен хранится в `sessionStorage`, не в URL и не в постоянном `localStorage`. HTTP-команды передают его через `X-Player-Token`; WebSocket передаёт токен в первом сообщении. Backend повторно проверяет полномочия для каждой команды. Скрытие элементов UI не является механизмом авторизации.

Текущая модель рассчитана на доверенную локальную сеть. Перед публикацией за её пределами необходимы HTTPS, управление отзывом/ротацией токенов и дополнительные меры защиты браузерной сессии.
