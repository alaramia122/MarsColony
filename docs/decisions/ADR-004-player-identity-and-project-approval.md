# ADR-004: Идентификация игроков, полномочия и согласование проектов

- **Статус:** принято для первого вертикального среза этапа 2
- **Дата:** 2026-11-15

## Контекст

Игровая сессия становится многопользовательской. Сервер должен отличать участников, ограничивать действия их полномочиями и сохранять проверяемую историю согласований. Клиентский идентификатор игрока не может служить доказательством личности: его можно подменить.

## Решение

1. Участник принадлежит ровно одной игровой сессии. Идентификация в MVP выполняется случайным bearer credential, выдаваемым сервером при присоединении; в БД хранится только криптографический хеш токена.
2. Присоединение выполняется по секретному коду приглашения сессии. Код и токен генерируются криптографически стойким генератором; открытые значения не сохраняются в БД.
3. Роли назначаются участнику внутри сессии. Направления ответственности задаются кодами из фиксированного каталога 16 направлений. Полномочие всегда проверяется в контексте конкретной сессии и конкретного действия.
4. Проект — отдельная сущность с автором, затрагиваемыми направлениями, сроком, бюджетом, потребностями в ресурсах, ожидаемым результатом и версией состояния.
5. Переходы проекта задаются конечным автоматом: draft → submitted → approved/rejected → executing → completed/cancelled. Недопустимый переход отклоняется сервером.
6. Требования к согласованию формируются детерминированно из затрагиваемых направлений и типа проекта. Голосование доступно только участникам с соответствующим полномочием; автор проекта не подтверждает собственную заявку.
7. Денежные средства резервируются атомарно при переводе проекта из draft в submitted, чтобы конкурирующие заявки не могли занять один и тот же бюджет. Резерв освобождается при отклонении/отмене; фактическое списание выполняется при запуске исполнения.
8. Каждое решение и переход состояния создаёт append-only событие. Конкурентные изменения защищаются блокировкой строки проекта/сессии и проверкой ожидаемой версии.
9. Проектные команды не вызывают расчётный движок напрямую из клиента. Сервер проверяет полномочия, бюджет, доступность ресурсов и предусловия, затем выполняет переход.

## Последствия

- Для MVP не требуется внешняя система учётных записей; bearer token является локальным credential сессии.
- Потеря токена означает необходимость перевыпуска/повторного приглашения администратором сессии; механизм восстановления аккаунта относится к более позднему этапу.
- Матрица ролей и полномочий должна быть явной, версионируемой и покрытой тестами.
- Политика согласования является частью правил сценария и может уточняться без изменения базовой модели проекта.
- Аутентификация защищает доступ к сессии, но не заменяет HTTPS при сетевом развёртывании.
