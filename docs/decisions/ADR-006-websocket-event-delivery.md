# ADR-006: доставка обновлений браузерным клиентам

- **Статус:** принято
- **Дата:** 2026-11-15
- **Контекст:** этап 3 MarsColony

## Контекст

Общий экран и персональные кабинеты должны отображать согласованное состояние одной игровой сессии. Backend уже хранит состояние и append-only журнал событий в PostgreSQL. Клиентам требуется оперативно узнавать о новых изменениях и восстанавливаться после потери соединения.

## Решение

1. HTTP API остаётся интерфейсом чтения состояния и отправки команд.
2. WebSocket используется как канал уведомлений о новых commit-событиях.
3. После соединения клиент проходит аутентификацию сессионным bearer token в первом WebSocket сообщении. Токен не помещается в URL.
4. Сервер отправляет полный snapshot и high-water sequence, затем события журнала с большей последовательностью.
5. В первом MVP новые события обнаруживаются polling-запросом к PostgreSQL с интервалом 750 мс.
6. Клиент воспринимает событие как сигнал перечитать HTTP snapshot; он не применяет event payload к локальному игровому состоянию.
7. При reconnect сервер снова отправляет полный snapshot. Это является механизмом восстановления пропущенных обновлений.
8. Backend проверяет сессию и участника независимо от состояния UI. WebSocket-подписка не предоставляет права изменять состояние.

## Последствия

- Журнал PostgreSQL остаётся единственным устойчивым источником последовательности событий.
- Реализация не требует отдельного брокера сообщений и работает в текущем модульном монолите.
- Polling создаёт дополнительную нагрузку на БД, пропорциональную числу активных соединений. Для масштаба за пределами LAN MVP следует оценить LISTEN/NOTIFY или брокер.
- Полный snapshot при каждом reconnect проще и надёжнее сложного восстановления локального состояния, но передаёт больше данных.
- WebSocket обеспечивает доставку уведомлений; фактическое состояние всегда подтверждается HTTP API.
