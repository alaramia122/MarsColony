# Этап 2 — участники, полномочия и проекты

**Статус:** первый backend-вертикальный срез реализуется в ветке `feat/stage2-players-projects`.
**Связанная задача:** [Issue #7](https://github.com/alaramia122/MarsColony/issues/7).

## 1. Модель участника

Участник привязан к одной игровой сессии. Сервер выдаёт ему случайный bearer token; в PostgreSQL хранится только SHA-256 хеш. Присоединение выполняется по секретному коду приглашения, также хранимому только в виде хеша. Открытые значения возвращаются только при создании сессии или присоединении и не включаются в последующие ответы.

Стартовый участник-создатель получает роль `colony_commander`. Новые участники получают базовую роль `player`. Командир назначает роли и направления ответственности.

### Роли первого среза

| Код | Назначение |
|---|---|
| `colony_commander` | Управление сессией, назначение ролей, полный контроль проектов и продвижение периода |
| `domain_lead` | Подготовка, согласование, исполнение и завершение проектов в назначенных направлениях |
| `finance_lead` | Финансовое согласование проектов с ненулевым бюджетом |
| `engineer` | Инженерная роль; детальные разрешения будут расширены в следующих итерациях |
| `player` | Участие в сессии и чтение доступного состояния |

Полномочия всегда проверяются в контексте сессии. Роли не являются глобальными правами пользователя.

## 3. Проектная карточка

Карточка содержит:
- название и описание;
- тип проекта;
- одно или несколько затрагиваемых направлений;
- автора;
- запрашиваемый бюджет в игровых кредитах;
- длительность в игровых периодах;
- требования к ресурсам из каталога текущего сценария;
- ожидаемый результат в структурированном виде;
- статус, версию и историю согласований.

Первый каталог типов: строительство, производство, ремонт, исследование, разведка, закупка, инфраструктура и прочие типовые действия.

## 4. Жизненный цикл

`draft → submitted → approved → executing → completed`

Альтернативные конечные состояния: `rejected`, `cancelled`.

- Автор или командир отправляет черновик на согласование.
- В момент отправки сервер блокирует строку сессии, проверяет доступный бюджет и резервирует сумму. Это предотвращает двойное распределение бюджета конкурирующими заявками.
- Для каждого затрагиваемого направления требуется согласование его руководителя. Для проекта с ненулевым бюджетом требуется финансовое согласование. При голосовании сохраняется снимок роли и направлений ответственности участника, поэтому последующее переназначение ролей не переписывает историю полномочий.
- Командир может закрыть все требования согласования одним решением, если он не является автором проекта.
- Автор проекта не согласует собственную заявку.
- После полного набора согласований проект становится `approved`.
- Уполномоченный участник запускает проект: зарезервированная сумма списывается из бюджета, резерв освобождается, статус становится `executing`.
- Уполномоченный участник отмечает завершение. Отклонение или отмена до запуска освобождает резерв.

Текущая реализация списывает бюджет при запуске. Фактическое потребление материалов, назначение персонала и изменение производственных мощностей будут подключены к расчётному движку в следующих итерациях этапа 2.

## 5. API первого среза

Все endpoints находятся под `/api/v1`. Для действий участника передаётся заголовок `X-Player-Token`.

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/sessions` | Создать сессию и получить credentials владельца |
| POST | `/sessions/{id}/players` | Присоединиться по коду приглашения |
| GET | `/sessions/{id}/players` | Список участников |
| PUT | `/sessions/{id}/players/{player_id}/roles` | Назначить роли и направления |
| GET | `/sessions/{id}` | Прочитать состояние и журнал |
| POST | `/sessions/{id}/advance` | Продвинуть период (командир) |
| POST | `/sessions/{id}/projects` | Создать проект |
| GET | `/sessions/{id}/projects` | Список проектов |
| POST | `/sessions/{id}/projects/{project_id}/submit` | Отправить на согласование |
| POST | `/sessions/{id}/projects/{project_id}/approvals` | Согласовать или отклонить |
| POST | `/sessions/{id}/projects/{project_id}/execute` | Запустить исполнение |
| POST | `/sessions/{id}/projects/{project_id}/complete` | Завершить исполнение |
| POST | `/sessions/{id}/projects/{project_id}/cancel` | Отменить до запуска |

Команды изменения проекта передают `expected_version`. Несовпадение версии возвращает HTTP 409. Все изменения сессии и события журнала записываются в одной транзакции; записи событий имеют монотонную последовательность в пределах сессии.

## 6. Инварианты

1. Нельзя использовать token из другой сессии.
2. В базе не хранится открытый player token или invite code.
3. Нельзя назначить неизвестную роль или направление.
4. Domain lead может действовать только в назначенных направлениях.
5. Нельзя согласовать собственный проект или голосовать повторно.
6. Нельзя отправить проект с неизвестным ресурсом или отрицательной потребностью.
7. Нельзя зарезервировать больше доступного бюджета с учётом ранее созданных резервов.
8. Отклонение/отмена освобождает резерв; запуск атомарно списывает бюджет.
9. Все переходы статусов и финансовые операции имеют audit event.
10. Устаревшая команда не изменяет проект.

## 7. Ограничения первого среза

- Bearer credentials предназначены для локальной игровой сессии. Перед развёртыванием за пределами доверенной LAN необходим HTTPS.
- Восстановление утраченного токена, отзыв сессии и управление списком приглашений пока не реализованы.
- Роль `engineer` пока не предоставляет самостоятельных разрешений.
- Проектная карточка и согласование готовы как серверный workflow; исполнение ещё не создаёт физические объекты, не назначает персонал и не потребляет материалы. Это следующий вертикальный шаг.
- Авторизация чтения сессии и продвижения периода включена в этот срез; продвижение периода доступно командиру.
